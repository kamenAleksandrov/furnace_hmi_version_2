# Requirements baseline

This file is the normative requirements register for accepted project behavior.
An ID remains stable after publication; change its text deliberately and record
consequential changes in an ADR. Implementation and verification status are
tracked separately in [traceability](../06-testing/TRACEABILITY.md).

## Functional requirements

| ID          | Requirement                                                                                                                                                                                                                                        |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REQ-FUN-001 | The HMI shall act as a remote operator interface and shall present authoritative operational state received from the Control CPU.                                                                                                                  |
| REQ-FUN-002 | Program browsing and editing shall use an HMI-local draft, while the Control CPU shall own validation, identifiers, revisions, persistence, and the authoritative program library.                                                                 |
| REQ-FUN-003 | Operators shall generally be able to navigate, inspect data, and manage program drafts while a run is active, subject to explicit controller permissions rather than a global UI lock. The current Program-run workflow is an explicit product exception: while an active or paused Program is presented, the HMI shall remain on its dedicated Program-running view and suppress ordinary bottom navigation until normal Stop. This presentation containment neither stops the furnace nor substitutes for controller permission or safety policy. |
| REQ-FUN-004 | Manual shall be a first-class controller mode supporting Start, target/rate changes, Pause, Resume, and Stop; it shall not be represented as a synthetic program.                                                                                  |
| REQ-FUN-005 | The Control CPU shall enforce the selected Manual session deadline. The default selection shall be six hours and the UI shall permit an explicit longer duration up to the controller's configurable maximum Manual heating duration (initially 48 hours, furnace MAN-01); the six hours is a default, not a maximum. Target/rate changes shall not reset the deadline. Exact expiry behavior is open. |
| REQ-FUN-006 | The operator interface shall support Start, Pause, Resume, and normal software Stop as controller requests.                                                                                                                                        |
| REQ-FUN-007 | After link loss or HMI restart, the HMI shall identify the current controller session, invalidate incompatible pending/cache state, obtain authoritative state, and reconstruct its presentation.                                                  |
| REQ-FUN-008 | The HMI information model shall be able to represent the dashboard baseline described in [UX and domain baseline](../03-hmi/UX_AND_DOMAIN_BASELINE.md) without imposing a rigid fixed screen layout.                                               |
| REQ-FUN-009 | The HMI shall support planned and live measured temperature trajectories; their semantic relationship to controller execution shall be explicit. The view shall label its time and temperature axes, render the planned path as a muted solid reference and the measured path as a contrasting solid path above it, and show unavailable measurements as gaps rather than invented values. For an active run, its initial domain shall show the complete controller-accepted predicted trajectory with deliberate headroom and shall expand only when a live measured time or temperature leaves that domain. |
| REQ-FUN-010 | Each setting shall have an explicit HMI or Control CPU owner. Controller-owned settings shall be presented from controller-provided value, writability, and applicable metadata.                                                                   |
| REQ-FUN-011 | The Control CPU shall own operational counters and authoritative clock/time; the HMI shall display controller-provided values.                                                                                                                     |
| REQ-FUN-012 | Run history shall consist of immutable Run Sessions. Reuse shall create an editable draft rather than alter history.                                                                                                                               |
| REQ-FUN-013 | The UI shall be localizable from the start, with English as the only initially implemented language and visible strings separated from screen logic.                                                                                               |
| REQ-FUN-014 | Celsius shall be the initially implemented display unit; canonical model representation and presentation boundaries shall not prevent later display-unit support.                                                                                  |
| REQ-FUN-015 | Future reset, clear, and restart operations shall have separately defined ownership, scope, and permission semantics rather than one ambiguous factory-reset operation.                                                                            |
| REQ-FUN-016 | The Control CPU shall own service-period state and proposed-run service evaluation. When its configured policy requires it, the Control CPU shall issue one service-period acknowledgement opportunity, record an accepted acknowledgement for later Device/maintenance inspection, and allow ordinary operation after the accepted acknowledgement subject to all other controller policy. The HMI may present the correlated acknowledgement dialog but shall not authorize, record, suppress, or bypass the policy locally. |
| REQ-FUN-017 | The HMI shall let an operator create and edit a local ProgramDraft with ordered HEATING, HOLD, and COOL StageDrafts, using current-session Control CPU capability metadata for syntax/range assistance. HEATING draft assistance shall let the operator set target temperature and either positive °C/min or duration, calculating the other value from its local estimation context; initial controls use 1 °C, 0.1 °C/min, and 1-minute increments. HOLD shall take duration and present an inherited/estimated target; COOL shall take target temperature and optionally a controlled cooling rate, with no selected rate meaning a request for the controller's fastest permitted cooling. These are HMI assistance rules only: the Control CPU shall validate and accept or reject every submitted draft. |
| REQ-FUN-018 | The HMI shall send a Start request only for an explicit operator Start action in the current controller session. It shall not store, queue, arm, schedule or automatically repeat a Start or a start confirmation, including after a temperature change, cooling into an eligible range, cancellation, expiry, link loss and recovery, HMI restart, or controller restart. A waiting-for-cooling presentation is informational only. Governing furnace requirement: START-01 ([ADR-0013](../07-decisions/0013-explicit-start-and-hot-start.md)). |
| REQ-FUN-019 | When the Control CPU returns a hot-start proposal, the HMI shall present, before any confirmation, the measured temperature with its validity (refreshed at the defined reporting interval), the proposed starting stage, every stage that would be skipped, the skipped Hold durations, the controller's incomplete-treatment warnings, and explicit Confirm and Cancel actions. The confirmation has no normal timeout: it stays open while valid live data and a live controller link exist. When the controller publishes a changed proposal, the HMI shall show the change clearly and require confirmation of the new proposal; Confirm always refers to the proposal revision on screen and is a request the controller revalidates and may reject. All text comes from the shared string catalogue with typed parameters (REQ-FUN-013). Governing furnace requirements: START-02, START-05 ([ADR-0013](../07-decisions/0013-explicit-start-and-hot-start.md), [ADR-0014](../07-decisions/0014-live-hot-start-confirmation-and-sensor-faults.md)). |
| REQ-FUN-020 | Program names and other operator-entered text shall be UTF-8, including Cyrillic. Length limits are counted in characters and come from the controller capability report (furnace PROG-09: 1-31 characters); font coverage for non-Latin scripts follows [ADR-0012](../07-decisions/0012-theme-and-language-catalogues.md). |
| REQ-FUN-021 | The HMI shall indicate loss of communication or of current telemetry, disable Confirm while data is stale or unavailable, and inform the operator with the controller's reason when a hot-start proposal is invalidated or a configured fallback timeout applies. It shall never dismiss a confirmation silently or present it as accepted; after any invalidation the operator must start again explicitly. Governing furnace requirement: START-11 ([ADR-0014](../07-decisions/0014-live-hot-start-confirmation-and-sensor-faults.md)). |
| REQ-FUN-022 | The HMI shall present controller sensor-fault events (affected channel, classification, operational consequence, required operator action) as localized warnings and shall show degraded operation distinctly from normal operation. Acknowledging a warning shall not bypass a fault, and a cleared fault shall not restart heating; Resume is an explicit operator request. A failure of a sensor required for control or protection is a latched critical fault without Resume (REQ-FUN-026, REQ-FUN-027; amended 2026-10-22). Governing furnace requirements: SENS-01, SENS-03, SENS-04, SENS-05, SENS-07 ([ADR-0014](../07-decisions/0014-live-hot-start-confirmation-and-sensor-faults.md), [ADR-0018](../07-decisions/0018-fault-manager-and-hold-approach-presentation.md)). |
| REQ-FUN-023 | A cooling-time estimate, if offered, is optional and informational: it shows "no reliable estimate" when the controller reports none, is never presented as a guaranteed time, and never triggers a Start. Governing furnace requirement: START-08. |
| REQ-FUN-024 | During a Hold stage the HMI shall present, from the controller's Hold progress only, which of these states applies: approaching Hold temperature; waiting for stable temperature; stability qualification in progress; active Hold treatment; treatment interrupted or out of tolerance; Hold completed. The treatment countdown shall appear only during active treatment and show the controller's remaining treatment time; it shall never start at stage entry or during qualification, including after a hot start into a Hold. Elapsed stage time and credited treatment time shall remain distinguishable, and an interrupted treatment shall never be shown as progressing or completed. After an interruption or a Pause the credited time stays visible, requalification is shown as such, and the countdown resumes from the kept time only when the controller reports active treatment again. All labels come from the shared string catalogue with typed parameters (REQ-FUN-013). Governing furnace requirements: PROF-03, PROF-07, PROF-11, PROF-12, PROF-13, START-09 ([ADR-0015](../07-decisions/0015-hold-qualification-and-treatment-time.md), [ADR-0016](../07-decisions/0016-program-execution-presentation.md)). |
| REQ-FUN-025 | During program execution the HMI shall present, from controller status and events only: the current stage and execution phase; the requested setpoint and the measured process temperature; whether the ramp is progressing, held back (with the tracking deviation and holdback time) or waiting at the target; actual elapsed time and nominal time, with any delay; controller warnings and faults; and, when paused, whether the operator or a fault paused the run and why. Pause, Resume and Stop are controller requests; a rejected Resume shows the controller's blocking conditions; the HMI never resumes or retries on its own, also not when the temperature or a fault clears. At the end it shows the controller's outcome (completed, completed with deviations requiring review, stopped by the operator, interrupted by a fault, prevented by protection) and never presents curing as accepted while the controller reports it as not assessed. All labels come from the shared string catalogue with typed parameters (REQ-FUN-013). Governing furnace requirements: PROF-01, PROF-02, PROF-08, PROF-13, PROF-16, START-15, RUN-07 to RUN-11, GUARD-01 ([ADR-0016](../07-decisions/0016-program-execution-presentation.md)). |
| REQ-FUN-026 | The HMI shall present, from controller status and events only: a run latched in the faulted state (critical fault or protective trip) distinctly from any pause, with its fault class and reasons, without a Resume action and with Stop as the only run command; a protective trip as an action of the independent protection that the HMI cannot clear or bypass; the outcome "interrupted by a critical fault"; a stage-transition deviation above the controller's threshold as a review reason with its measured value; and, in a diagnostics or service view only, the controller's heating-power request, control error and saturation flags. Acknowledging or dismissing a fault shall never resume or restart heating, and a power request shall never be presented as proof that power flowed. All labels come from the shared string catalogue with typed parameters (REQ-FUN-013). Governing furnace requirements: FAULT-03, FAULT-04, RUN-12, CTRL-09, CTRL-10, GUARD-05 ([ADR-0017](../07-decisions/0017-fault-classes-and-control-diagnostics-presentation.md)). |
| REQ-FUN-027 | The HMI shall present, from controller fault status, entries and events only: the active fault entries with class, condition, latch, acknowledgement, occurrence count and recovery eligibility; the reasons heating is currently inhibited; and the fault event history in sequence order, showing a sequence gap as missed events. Acknowledge and recovery shall be controller requests whose results are shown; acknowledgement shall never hide an entry that still inhibits heating and shall never be presented as recovery or Resume; no local role, password or override shall exist. A failure of a required sensor shall be shown as a latched critical fault. During a Hold whose setpoint is still approaching its target, the setpoint shall be shown moving toward the target while qualification may already run. All labels come from the shared string catalogue with typed parameters (REQ-FUN-013). Governing furnace requirements: FAULT-01, FAULT-05, FAULT-06, SENS-03, SENS-07, RUN-13 ([ADR-0018](../07-decisions/0018-fault-manager-and-hold-approach-presentation.md)). |
| REQ-FUN-028 | The HMI shall present, from controller status, proposals and events only: an advisory (recommended) program duration in a Start proposal as a warning with the recommended, estimated and maximum durations and an explicit acknowledgement whose accepted duration is sent with the confirmation, never as permission beyond the maximum; the accepted duration, the runtime used and the hard runtime boundary separately from elapsed time; a program overrun as a warning and a stop at the runtime limit as not overridable; a run awaiting a quality decision with its reasons, the possible effect on curing quality, the recommended-action codes and the remaining decision time, offering exactly Continue and Stop as controller requests with visible results, and a decision timeout as a fault pause with heating off; faults grouped by category (quality, operational, equipment, safety), never offering Continue for an equipment or safety fault; tolerated Hold excursions and the Start measurement qualification as information; the execution temperature labelled as chamber temperature; and a completed program never as a verified cure. No role, login or local override shall exist. All labels come from the shared string catalogue with typed parameters (REQ-FUN-013). Governing furnace requirements: PROG-11, PROF-15, PROF-17, RUN-14, RUN-15, RUN-16, START-16, START-17, FAULT-07, FAULT-08, FAULT-09 ([ADR-0019](../07-decisions/0019-duration-decisions-and-runtime-presentation.md)). |

## Non-functional requirements

| ID | Requirement |
| --- | --- |
| REQ-NFR-001 | Operator interaction shall produce perceptible local feedback immediately. Ordinary controller operations should provide meaningful response or pending/progress presentation within approximately 500 ms. |
| REQ-NFR-002 | Normal Stop handling shall have stronger responsiveness than low-priority operations and shall not be blocked by filesystem, graph, telemetry, modal, or draft-editing work. |
| REQ-NFR-003 | Low-priority HMI requests and droppable/coalescible telemetry shall not delay important command responses, fault/state events, or furnace-critical Control CPU work. |
| REQ-NFR-004 | The GUI context shall not perform long or unbounded filesystem, controller, storage, retry, or bulk-processing work. Cross-context mechanisms shall be explicit and bounded. |
| REQ-NFR-005 | The source architecture shall support multiple target-specific Zephyr builds and a desktop build without redesigning the portable HMI application. |
| REQ-NFR-006 | Every displayed engineering value shall distinguish its semantic provenance (measured, commanded, estimated, calculated, or configured) and validity (including stale or unavailable). |
| REQ-NFR-007 | An estimate derived from heater demand shall not be presented as measured electrical power. |
| REQ-NFR-008 | HMI health supervision shall eventually detect failure of critical HMI subsystems; an unrelated healthy thread shall not mask GUI, communication-owner, or critical-application failure. |
| REQ-NFR-009 | Hardware-specific values and APIs shall remain outside portable application code and be supplied through Zephyr-native configuration, drivers, and platform adapters. |

## Architecture invariants

| ID | Invariant |
| --- | --- |
| ARCH-INV-001 | The Control CPU is authoritative for furnace truth, programs, execution, validation, timing, control, faults, operational settings/counters, and safety; the HMI owns only presentation, local interaction state/drafts/preferences/cache, its client, and its own health. |
| ARCH-INV-002 | No furnace safety mechanism may depend on correct HMI operation. Emergency Stop is outside HMI software; normal Stop remains a distinct high-priority software request. |
| ARCH-INV-003 | Reconnection shall never automatically replay a previous command merely because the link returned. |
| ARCH-INV-004 | A newly started HMI shall be able to reconstruct correct operator-facing state from current authoritative controller information without requiring complete local event history. |
| ARCH-INV-005 | Only the designated GUI execution context may manipulate LVGL objects. |
| ARCH-INV-006 | Low-priority HMI/library work shall not impair controller control loops, sensors, watchdog, actuators, or safety/interlock handling. |
| ARCH-INV-007 | The Control CPU shall authoritatively validate every meaningful furnace operation; the HMI shall assume a request can be rejected. |
| ARCH-INV-008 | Operational limits shall not be hard-coded in the HMI as authority. Controller-informed constraints are usable only from a valid current-session capability snapshot. |
| ARCH-INV-009 | Active execution shall use an immutable controller-accepted program revision; later library edits shall not mutate it. |
| ARCH-INV-010 | Historical Run Sessions shall be immutable. |
| ARCH-INV-011 | The HMI and Control CPU watchdogs are independent; each processor owns its own health behavior. |

## Protocol requirements

These requirements constrain later protocol design; they do not define a wire
schema.

| ID | Requirement |
| --- | --- |
| PROTO-001 | Protocol semantics shall distinguish transmission, frame decode, queuing, acceptance/rejection, resulting state change, and completion when those distinctions matter. |
| PROTO-002 | The protocol shall provide controller boot/session identity and enough authoritative state to detect stale HMI state and reconstruct the operator view. |
| PROTO-003 | Request retry and duplicate behavior shall be explicit and shall not permit unintentional repeated operations. |
| PROTO-004 | Native C structures shall not define the wire format. Serialization shall use explicit fixed-width representations, units, bounds, versioning, and integrity behavior independent of padding, enum size, `size_t`, native `bool`, endianness, or SDK error values. |
| PROTO-005 | Protocol semantics, serialization, framing/integrity, and physical transport shall remain separable so the application can use RS-422/UART or an in-memory simulator transport. |
| PROTO-006 | Immediate command responses, state transitions, and faults shall take precedence over droppable/coalescible periodic telemetry where required. |
| PROTO-007 | Initial fast telemetry shall be configurable around 1 Hz, slow counters around 5 seconds, and large diagnostics/history on request; these rates shall not become fixed wire assumptions. |
| PROTO-008 | Controller capability and setting metadata shall be scoped to the identified current controller session and invalidated when that identity changes. |
| PROTO-009 | The protocol shall permit a controller rejection to carry sufficient stable meaning for the HMI to present the outcome without treating transport success as operation success. |
| PROTO-010 | Current-session controller information and start-preflight outcomes shall carry a stable service condition/gate and the display inputs needed for a service-period warning. An acknowledgement, when supported, is a correlated controller request whose acceptance or rejection remains authoritative. |
| PROTO-011 | A current-session capability snapshot shall expose the program-authoring limits and field applicability needed for HMI assistance, including supported stage kinds, editable fields, bounds, increments, and available cooling modes. The HMI shall invalidate this metadata with its controller session and the Control CPU shall revalidate submitted drafts. |
| PROTO-012 | Start, hot-start proposal (with proposal revision), confirmation, cancel, invalidation, rejection, Resume, sensor-fault and operating-mode semantics shall follow the single controller interface specification in the furnace repository `docs/interfaces/controller-hmi-interface.md` (version 0.2.0 draft). This repository shall not define competing stage-selection or eligibility logic. A confirmation shall be bound to the controller session, start transaction, proposal revision, program revision and proposed stage. |

## Verification requirements

| ID | Requirement |
| --- | --- |
| TEST-001 | Tests shall demonstrate that HMI syntax assistance cannot bypass authoritative controller rejection. |
| TEST-002 | Reconnect tests shall demonstrate cache invalidation, current-session reconstruction, and absence of automatic old-command replay. |
| TEST-003 | Snapshot tests shall demonstrate reconstruction without a complete prior event stream. |
| TEST-004 | Protocol tests shall cover duplicate, retry, timeout, rejection, late response, and controller boot/session-change cases once semantics exist. |
| TEST-005 | Concurrency tests/reviews shall verify exclusive LVGL ownership and bounded cross-context communication. |
| TEST-006 | Priority/fault-injection tests shall verify that telemetry and low-priority work do not obstruct Stop handling or important state/fault delivery. |
| TEST-007 | Planned-trajectory tests shall verify agreement with the same accepted semantics used for controller execution once stage semantics are defined. |
| TEST-008 | Build verification shall cover portable host code, the desktop simulator, and each declared supported Zephyr target as those targets are introduced. |
| TEST-009 | Service-policy verification shall demonstrate controller-owned one-time acknowledgement, recorded acknowledgement visibility, and rejection/invalidity handling across session changes. |
| TEST-010 | Program-authoring tests shall demonstrate that controller capability metadata guides HMI assistance without replacing controller validation, including stage-kind field applicability and invalid draft outcomes. |
| TEST-011 | Hot-start tests shall demonstrate that no Start or confirmation is sent without an explicit operator action (including after cooling into an eligible range, reconnect, HMI restart and controller restart); that the proposal view shows every REQ-FUN-019 item from controller data and stays open without a timeout while live data is valid; that a changed proposal is shown and only the current revision can be confirmed; that stale telemetry, link loss and invalidation disable Confirm and inform the operator (REQ-FUN-021); and that sensor-fault warnings and degraded mode are presented as specified without restarting heating (REQ-FUN-022). |
| TEST-012 | Hold presentation tests shall demonstrate, from scripted controller Hold progress, each REQ-FUN-024 state; that no treatment countdown is shown before the active-treatment state (also after a hot start into a Hold); that the displayed remaining treatment time equals the controller's value; that elapsed stage time and credited treatment time are shown distinctly; that an interrupted treatment is never shown as progressing or completed; and that after an interruption or Pause the kept credit and the requalification are shown and the countdown resumes from the kept time only in active treatment. |
| TEST-013 | Execution presentation tests shall demonstrate, from scripted controller status and events, every REQ-FUN-025 item: progressing ramp, holdback with deviation and time, waiting at the target, delay beyond nominal time, warnings, operator and fault pause with reasons, a blocked Resume with its conditions, no automatic resume, each outcome, and that curing is never shown as accepted while not assessed. |
| TEST-014 | Fault and diagnostics presentation tests shall demonstrate, from scripted controller status and events, every REQ-FUN-026 item: a critical fault and a protective trip each shown as a latched state distinct from a fault pause, no Resume action offered, a `FAULT_LATCHED` rejection shown, a latched state that stays shown after its trigger clears, no resume or restart after acknowledging, the critical-fault and protection outcomes, a transition deviation listed as a review reason, and diagnostics shown only in the diagnostics view and never used for decisions. |
| TEST-015 | Fault-manager and Hold-approach presentation tests shall demonstrate, from scripted controller status, entries and events, every REQ-FUN-027 item: entries with each class and recovery eligibility, inhibition reasons, an acknowledgement result that leaves an inhibiting entry visible, a refused recovery request with its reason, a required-sensor failure shown as latched and critical, a sequence gap shown as missed events, and a Hold setpoint shown approaching its target while qualification runs. |
| TEST-016 | Duration, decision and runtime presentation tests shall demonstrate, from scripted controller proposals, status and events, every REQ-FUN-028 item: an advisory-duration proposal with acknowledgement and the accepted duration in the confirmation, a rejected confirmation without it, runtime readings distinct from elapsed time, an overrun warning, a stop at the runtime limit, a decision view with countdown, Continue accepted and rejected, a decision timeout, an equipment or safety fault without Continue, an excursion count, the Start-qualification condition, the chamber-temperature label and a completed run not shown as a verified cure. |

## Deferred detail

Hot-start stage eligibility, the Hold entry tolerance and hot-start treatment
accounting are Control CPU decisions (furnace START-03, START-04, START-09);
sensor-fault classification and degraded-operation policies are Control CPU
policies validated per furnace model (furnace SENS-01 to SENS-03).
Stage semantics, Manual expiry transition, alarm workflow, Run Session schema and
retention, serialization/framing, exact transport parameters, memory budgets,
and production hardware are deliberately unresolved. See
[open questions](../09-progress/OPEN_QUESTIONS.md); do not infer answers from
examples in this repository.
